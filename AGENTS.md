# AGENTS.md

Paper Minecraft plugin (`HCCore`) for the Hack Club server. Java 21 + Gradle.

## Build & run

- `./gradlew build` — compiles and builds the **shadow** jar (the `build` task `dependsOn shadowJar`).
- Output jar for deploying: `build/libs/HCCore-Shadow-<version>.jar`. The plain `jar` task is the thin jar (`HCCore-<version>-thin.jar`) and is NOT what runs on the server.
- `./gradlew runServer` — starts a local Paper dev server (creates `run/`). Needs JDK 21; the build uses a Java 21 toolchain. CI's `setup-java` uses Java 17 but the toolchain still requires a JDK 21 to be available.
- There are **no tests, no lint, and no typecheck tasks** (no `src/test`). The only verification is `./gradlew build`.
- First `runServer` requires manually dropping `ProtocolLib` and `UltimateAdvancementAPI` jars into `run/plugins` (see `SETUP.md`). Both are hard `depend`s in `plugin.yml`, so the plugin won't enable without them.
- `scripts/deploy.sh` is stale (references a Maven `./target/HCCore.jar`); don't rely on it. `.vscode/tasks.json` is likewise stale. The real flow is `./gradlew build` then copy `build/libs/HCCore-Shadow-*.jar` to the server's `plugins/`.

## Architecture

- Entry point: `com.hackclub.hccore.HCCorePlugin` (`onEnable` wires everything).
- Commands are registered **twice**: in `HCCorePlugin.onEnable()` via `registerCommand(...)` and as entries in `src/main/resources/plugin.yml`. Adding one without the other leaves the command non-functional (`registerCommand` logs a severe if `plugin.yml` is missing the name).
- Per-player state lives in `PlayerData`, persisted as JSON (Gson) under `plugins/HCCore/players/<uuid>.json` via `DataManager`. Only fields annotated `@Expose` are saved/loaded; add `@Expose` for any new persistent field and load it in `PlayerData.load()`.
- Player-facing messages are MiniMessage classes in `playermessages/**` (static `get(...)` returning `Component`). Use `Placeholder`/`TagResolver`, not string concatenation.
- Slack bridge (`slack/SlackBot`) is optional and only constructed when `settings.slack-link.enabled` is true.

## Nametag rendering (non-obvious)

The overhead nametag is **not** driven by `Player#displayName(...)` or `playerListName(...)` — those only affect chat and the tab list. The vanilla nametag is rendered client-side as:

```
team.prefix + <GameProfile name from the PLAYER_INFO packet> + team.suffix
```

The GameProfile name is hard-limited to **16 UTF-16 units**; `team.prefix`/`team.suffix` are unlimited text Components. `NameChangeListener` (ProtocolLib) rewrites the profile name, and `PlayerData` splits a long nickname: first 16 units in the profile name (`getProfileName()`), remainder appended via the team suffix (`getNicknameOverflow()` + `updateTeamDecorations()`) so the full nickname shows on the vanilla name tag. The split never lands inside a surrogate pair. AFK and name color are also applied through the scoreboard team. Do not try to force names longer than 16 units into the GameProfile. Keep ProtocolLib support intact.
